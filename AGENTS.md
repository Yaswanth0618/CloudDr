Cloud Drop
Build a small file-sharing app with React, Next.js App Router, TypeScript, and Tailwind CSS. A user selects or drops a file, uploads it, chooses when the share link expires, and copies the link. A recipient opens the link and downloads the file while the link is active. The project owner is using this app to learn AWS by doing each cloud step personally.
Start here
- Inspect the repository and follow its existing package manager, scripts, and conventions. Scaffold the requested stack only if there is no app yet.
- Before making UI decisions or editing frontend code, read and apply .agents/skills/frontend-design/SKILL.md. If the file is absent, mention that and continue with the existing UI conventions or an accessible baseline.
- Begin with a local vertical slice using an explicitly local storage and metadata implementation. Exercise file selection, upload progress, completion, share-link copying, download, and expiry. Keep local mode independent of AWS credentials and visibly distinguish it from a live integration in status reports.
Mandatory AWS teaching checkpoints
The project owner performs every action in the AWS account. Before a phase needs a live AWS action, stop and hand off that action. This includes authentication and credentials, IAM changes, resource creation or configuration, deployments, live tests and logs, cleanup, and any use of AWS Console, CLI, SDK, infrastructure tools, or scripts against the account. Do not run live calls yourself or hide them inside a test or dev command. Writing integration code, IAM policy drafts, and example commands locally is fine. Complete independent local work before surfacing the checkpoint when practical.

For each checkpoint, give the owner:
1. The feature being unblocked and what the AWS service or setting does.
2. Any prerequisites and the target account context or Region. Ask only for choices you genuinely need. Check current AWS documentation before giving version-sensitive Console steps or commands and link to the relevant official pages.
3. A numbered Console walkthrough with exact settings and clearly marked placeholders. Include a CLI option if it helps the lesson, and label the commands as steps for the owner to run.
4. The expected result and a concrete verification step the owner can perform. Flag relevant costs or public exposure before they proceed.
5. Exactly what safe values or redacted results to report back. Never request passwords, keys, session tokens, client secrets, credential files, or live presigned URLs. Use a local AWS profile or deployment role for AWS credentials. Keep credentials and server settings out of browser bundles, chat, logs, and git.
End the checkpoint turn and wait for the owner's reply before advancing that AWS-dependent phase. A request to proceed is permission to resume local work using the owner's reported setup. Any further live AWS action gets its own handoff. If verification fails, help diagnose it from redacted information and supply the next manual step. If the owner skips a phase, continue any independent local work and report the skipped integration as pending.
Build sequence
1. Local prototype. Provide a keyboard-accessible upload picker alongside drag-and-drop, a progress indicator, error and retry states, expiration choices, and a recipient page for valid, expired, and missing shares. Keep production configuration explicit and fail clearly if it is missing.
2. AWS developer access and private S3. Walk the owner through the applicable AWS sign-in or local profile setup, then through creating a private bucket and granting narrowly scoped permissions. Keep S3 Block Public Access enabled and scope CORS to the app origins and methods in use. Have a server-only Next.js route issue short-lived, object-scoped upload authorization so the browser uploads directly to S3. Enforce a documented size limit both locally and using an S3-supported signed upload policy. Generate object keys on the server and verify the uploaded object before making its share link usable. Have the owner run the first real upload and verify the object in S3.
3. DynamoDB and expiring links. Walk the owner through creating the share metadata table and granting the app access. Store an opaque, unguessable share ID, object key, filename, and expiration timestamp. On each request to /s/[id], check the expiry on the server before authorizing a download. Cap the lifetime of the presigned download URL at the remaining share lifetime. Use DynamoDB TTL only for eventual metadata cleanup if enabled. S3 object cleanup is a separate step with its own checkpoint. Have the owner verify a valid share and an expired share with a test file.
4. Uploader sign-in. Treat application authentication as a separate milestone from AWS developer sign-in and IAM. Use Cognito when uploader sign-in is in scope. Before enabling it, stop and guide the owner through creating a user pool, configuring an app client and local callback and sign-out URLs, and creating a test user. Resume when the owner confirms setup and provides the Region, user pool ID, app client ID, and sign-in domain if needed. Use an appropriate OAuth flow and enforce uploader authentication in server routes that create or finalize uploads. Keep recipient links usable without an account. Have the owner verify sign-in, sign-out, and that signed-out visitors cannot create shares. Keep an unauthenticated prototype local until uploader access is protected.
5. Stretch goals. After the core flow works, add S3-triggered Lambda thumbnail generation for images or deploy the app if the owner requests it. Pause before creating or configuring each live resource and before live verification.
At each milestone run the repository's applicable local lint, typecheck, tests, and build. Report which behavior you verified locally and which live checks the owner confirmed. Never present a local mock as evidence that AWS is configured or working.
